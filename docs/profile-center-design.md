# 个人中心设计说明

> 第一版最终产品口径以 [MetroRestroom 第一版产品需求文档](./PRD.md) 为准；本文保留个人中心的设计细节与后续方向。

## 1. 设计目标

个人中心的定位不是登录入口，而是小程序的能力补充区和轻量运营区。
核心思路是：**急用时不添乱，闲时有趣味**。

首页继续保持工具效率和高级感，第一版优先承载查厕所、定位和站点拨轮；搜索、路线等能力后续再纳入首页。与身份、偏好、记录、趣味相关的内容，统一收敛到个人中心。

第一版页面范围确定为：

- 首页
- 个人中心
- 设置/关于
- 数据纠错入口

数据纠错入口可以从个人中心进入，具体页面结构在原型阶段细化。核心查厕流程不得依赖用户进入个人中心或完成登录。

第一版使用“首页 + 个人中心”两个底部 Tab；设置/关于和数据纠错从个人中心进入。

## 2. 身份与本地记录策略

第一版不提供显式登录页面，用户打开后直接使用以下能力：

- 查厕所
- 定位
- 站点拨轮
- 设置声音/震动
- 查看最近记录

最近记录、上次城市、线路、站点以及声音和震动设置保存在本地。后续增加搜索和路线能力时，也不应将登录作为使用前提。

云端操作使用微信小程序云开发自动注入的用户身份，由云函数在服务端取得 `OPENID`，不要求用户执行显式登录。`OPENID` 只用于纠错提交的限流、防滥用和问题追踪，不在前端展示或向其他用户传播。

## 3. 后续个人化能力

以下能力不进入第一版，后续确有跨设备账户需求时再设计授权和同步方式：

- 收藏站点
- 点赞厕所信息
- 打卡记录
- 个人统计

这些能力用于增强用户留存、提升数据质量，并形成个人使用习惯的沉淀。

## 4. 声音与震动设置

声音与震动属于高频交互偏好，第一版在个人中心或设置页提供独立开关。

确定策略如下：

- 拨轮音效默认开启
- 震动默认开启
- 个人中心支持独立开关
- 声音允许用户手动关闭
- 声音策略应尽量尊重系统静音状态，避免打扰

这里的原则是：交互反馈要明确，但不能制造噪音负担。

## 5. 趣味玩法方向

个人中心可以承接“使用痕迹”和“轻社交感”的趣味内容，但第一版要控制表达方式，避免过度娱乐化。

可考虑的方向：

- 如厕足迹
- 常去站点
- 救急次数
- 打卡

关于排行榜类玩法：

- “拉屎排行榜”或“蹲点排行榜”可以作为趣味方向讨论
- 排行榜和个人统计均不进入第一版，后续可优先从个人统计开始验证
- 不建议第一版做强公开排行榜

原因是公开排行榜容易带来以下问题：

- 低俗化风险
- 隐私暴露风险
- 刷榜和作弊风险

## 6. 产品原则

个人中心的设计原则如下：

- 不为了查厕所强制登录
- 首页保持工具效率，不被趣味内容打扰
- 趣味内容放在个人中心，作为增值体验
- 统计和荣誉感要克制，避免喧宾夺主
- 兼顾真实使用场景和长期留存

## 7. 第一版范围

第一版落地以下内容：

- 声音与震动独立开关
- 最近记录本地保留
- 厕所数据同步状态：显示与首页一致的状态圆点和紧凑时间，但不重复提供手动更新入口
- 设置/关于页面
- 数据纠错入口

关于页只在正式版显示微信账号信息接口返回的真实版本号；开发版和体验版隐藏版本行，不显示“开发版”占位。微信客户端会自动检查小程序代码包更新，因此不增加手动“检查小程序更新”入口。厕所数据同步状态属于业务数据能力，固定放在个人页，不与小程序代码版本混用。

个人中心在同一“关于”卡片中提供两个平级入口：“关于 Metro 洗手间”继续只承载数据来源与版本信息；“作者寄语”进入独立页面。作者寄语以短句和短段落呈现，先说明即使知道站点有卫生间，缺少站内外、闸内外、是否需要出站以及车头、车尾或换乘通道等明确位置，仍然很难快速找到；再说明真实需求、“打开即用，用完即走”的轻量定位、独立 App 与微信小程序的使用成本差异、现有同类小程序的体验不足、官方公开数据基础、逐站实地核查计划与人力边界。正文采用普通页面排版，不使用引用框、左侧竖线或大块卡片；字号应适合移动端持续阅读。两个页面职责分离，避免把叙事内容混入信息型关于页，也不在个人中心首页直接展开长文。“关于”和“作者寄语”页均在正文末尾提供弱层级但足够大的“返回我的”操作；有上一页时调用返回，无上一页时切回“我的”Tab，确保页面被单独打开时也不会困住用户。

数据纠错不要求显式登录，提交内容包括线路、站点、问题类型、补充说明和可选联系方式。纠错记录通过云函数写入待审核数据，不直接修改正式厕所数据。

暂不建议第一版重点投入：

- 强公开排行榜
- 复杂好友体系
- 过度游戏化的成就体系
- 收藏、点赞、打卡和个人统计

## 8. 结论

个人中心的价值在于补齐“身份、偏好、记录、趣味”四类能力，但不能影响主流程。  
整体策略应保持克制，让小程序在“急用”时足够快，在“闲时”时也有一点可玩性。
