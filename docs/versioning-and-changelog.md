# 小程序版本与更新记录规范

本文是 MetroRestroom 小程序代码版本号、功能版本分组、环境流转和用户更新记录的固定规范。CloudBase 数据协议中的 `V1／V2`、`schemaVersion` 和数据快照版本不属于小程序代码版本，不使用本文规则。

## 1. 版本格式

所有小程序版本统一写为 `MAJOR.MINOR.PATCH`，必须包含三个非负整数，例如 `1.2.5`。界面、文档和更新记录均不添加 `V` 前缀，也不单独显示只有两段的 `1.2`。

| 变化位置 | 含义 | 适用范围 | 示例 |
|---|---|---|---|
| `MAJOR` | 产品大版本 | 核心定位、产品范围、信息架构或主要使用方式发生代际变化 | `1.9.3 → 2.0.0` |
| `MINOR` | 重点功能版本 | 新增或重做一个用户可感知的主要功能，形成新的 `X.X` 功能系列 | `1.1.5 → 1.2.0` |
| `PATCH` | 细节版本 | 在当前 `X.X` 功能系列内做修复、优化、补充和小范围调整 | `1.2.5 → 1.2.6` |

同一版本同时包含多类改动时，按影响最高的一类升级：`MAJOR > MINOR > PATCH`。提升 `MAJOR` 时将后两位归零；提升 `MINOR` 时将 `PATCH` 归零。版本数字不得有前导零。

新增城市不自动升级产品大版本，也不按城市顺序产生 `2.0.0／3.0.0`。新城市带来独立、明显的用户功能时提升 `MINOR`；仅扩充或修正已有城市数据时使用当前系列的 `PATCH`，并在更新记录中写明城市名称和用户可见变化。

当前里程碑口径：

- `1.0.0`：上海首发，支持地铁卫生间查询。
- `1.1.0`：新增轮盘式站点浏览。
- `1.1.1`：支持左右滑动切换换乘线路。
- `1.2.0`：支持智能定位与手动选站。
- `1.2.1`：升级站点数据与范围判定。
- `1.2.2`：新增行程预估与数据来源说明。
- `1.2.3`：新增分享功能和系统基础能力。
- `1.2.4`：升级前台实时定位。
- `1.2.5`：优化智能定位体验与版本记录。

## 2. 环境与版本流转

同一个版本按 `开发版 → 体验版 → 正式版` 流转，环境变化本身不产生新版本号。

- 三个环境可以暂时运行不同版本。当前已确认事实为：正式版 `1.2.3`、体验版 `1.2.4`、开发版 `1.2.5`。
- 已上传、分发、提交审核或正式发布的版本号不得复用，也不得在内容变化后继续沿用。
- 开发版完成并准备上传体验版时确定唯一版本号，同时完成更新记录。
- 更新日期在开发／体验阶段记录为该版本完成并可分发的日期；正式发布后可校正为微信后台实际发布日期。

从当前开发版 `1.2.5` 继续开发时：

- `1.2.5` 尚处于开发阶段且未形成不可复用的上传代码包时，经确认的同系列优化继续归入 `1.2.5`。
- `1.2.5` 上传、分发或冻结后，当前功能系列的后续细节修复或优化使用 `1.2.6`。
- 有新的重点功能：`1.3.0`。
- 产品代际变化：`2.0.0`。

## 3. 更新页分组与展示

更新页按前两位 `MAJOR.MINOR` 分组，但界面不显示只有两位的分组名。每个功能版本系列在主表只占一行，显示该系列最新的完整三位版本号：

- `1.2` 系列当前显示 `1.2.5`。
- `1.1` 系列当前显示 `1.1.1`。
- `1.0` 系列当前显示 `1.0.0`。
- 如果以后新增 `1.2.6`，主表中的 `1.2.5` 自动替换为 `1.2.6`，旧记录进入该行下拉区域。

点击存在历史记录的主表行后，在下方展开同一 `X.X` 系列的旧版本。下拉区域继续使用完整的“日期／版本／主要更新”三列表格行，不缩进为项目符号，也不混入其他 `X.X` 功能系列。没有旧版本的功能系列不显示下拉箭头。

当前 `1.2.5` 展开后依次显示 `1.2.4`、`1.2.3`、`1.2.2`、`1.2.1`、`1.2.0`；`1.1.1` 展开后显示 `1.1.0`；`1.0.0` 没有旧版本，不提供空下拉。

## 4. 更新记录数据格式

每个真实版本保存一条扁平记录，页面根据版本号前两位自动分组：

```js
{
  version: '1.2.5',
  date: '2026-08-23',
  summary: '优化智能定位体验与版本记录'
}
```

- `version` 必须唯一，且始终使用三个数字。
- 记录按版本从新到旧排列。
- `summary` 只写一句用户能理解的主要事项，不写 Commit 名、接口名或内部实现。
- 默认只加载一屏功能版本系列；超出时按 `X.X` 系列显示“点击查看更多”，不按单个细节版本分页。

## 5. Git、上传与发布节点

以下节点含义不同，必须分别记录：

1. `commit`：一个可回溯的代码改动单元；一个版本通常包含多个提交，提交不自动产生新版本。
2. `push`：将本地提交同步到远端；只证明代码已推送，不代表微信后台已有新代码包。
3. 上传开发版／体验版：在微信后台生成候选代码包；上传前必须确定版本号、对应 Commit 和更新记录。
4. 提交审核：候选版本进入微信审核，尚未正式上线。
5. 发布：微信后台完成正式发布后，才可标记为正式版本。

建议每次准备体验版建立明确提交，例如 `chore: 准备 1.3.0 体验版`。是否执行 Push、上传、审核和发布仍分别确认，不从任一前置节点推断后续授权。

## 7. 每次版本维护清单

1. 从上一个版本节点检查 Git 提交、Push 节点、`ROADMAP.md` 和相关产品文档。
2. 判断本次属于产品大版本、重点功能版本还是当前功能系列的细节版本。
3. 按用户可见结果合并事项，不直接把每个 Commit 转成一条更新记录。
4. 更新环境版本映射、更新记录、本文的版本审计表和必要产品文档。
5. 完成本地回归和微信开发者工具验证。
6. 准备体验版时记录版本号、Commit 和上传日期；审核、正式发布后继续补充真实状态和日期。
