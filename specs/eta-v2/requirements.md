# ETA V2 与多城市数据交付需求

## 1. 背景

当前预计耗时把乘车、掉头、换乘候车、换乘步行和前往卫生间分别表示为宽区间，再将各段最小值和最大值累加。行程越长，区间越容易被放大，最终可能出现最大值接近最小值两倍的结果，不能为用户提供足够明确的判断。

同时，上海卫生间原始数据、线路拓扑、坐标、入口和预计耗时规则分散在 Excel 与多个代码数据文件中。新增杭州、南京等城市前，需要统一人工采集模板、线上维护模型和本地发布格式，但不能破坏现有完整基础数据随包、弱网可查询的产品边界。

## 2. 目标

1. 将卡片预计耗时收敛为一个可解释、可回归的单值。
2. 使用离线固化的官方公开时刻与相邻站时分替代全网统一的宽区间。
3. 为环线、支线、跨线换乘、同站设施和缺失数据定义稳定边界。
4. 建立“一城一 Excel 工作簿、字段统一”的采集与导入规范。
5. 保持完整本地基础数据和离线查询能力，由 CloudBase 作为审核后的统一维护与发布源。
6. 让小规模数据优先整批发布和原子切换，避免为形式上的按线路拆分增加失败面。

## 3. 非目标

- 不提供实时列车位置、实时到站倒计时或拥挤度预测。
- 不纳入节假日临时加开、临时缩短间隔、故障、封站等临时运营调整。
- 不远程下发 WXML、WXSS、JavaScript、动效或其他 UI 代码。
- 不建立任意两站固定耗时矩阵；任意路径耗时必须由图上的基础边累加得到。
- 本轮不创建 CloudBase 集合、不修改权限、不上传数据，也不部署云函数。

## 4. 用户故事

- 作为正在乘车的用户，我希望看到“约 X 分钟”而不是跨度过大的区间，以便快速判断是否值得前往目标站卫生间。
- 作为数据维护者，我希望每个相邻站时分都有来源和核实状态，以便知道哪些值来自官方、哪些仍是降级估算。
- 作为城市扩展维护者，我希望复制同一份空白工作簿就能开始杭州或南京的数据整理，而不需要重新设计字段。
- 作为弱网用户，我希望云端检查失败时仍能继续使用随小程序发布的完整基础数据。

## 5. 验收需求

### R1：单值展示

- 当目标站存在卫生间且预计耗时可计算时，系统应只展示 `约 X 分钟`，不得同时向用户展示最小值和最大值。
- 当总耗时大于 0 秒时，系统应先以秒完成全部计算，再按以下阶梯取最近刻度，并保证最小展示值为 1 分钟：原始结果小于 10 分钟时取最近 1 分钟；10—30 分钟（含边界）取最近 2 分钟；大于 30 分钟时取最近 5 分钟。
- 当目标站没有卫生间记录时，系统不得展示预计耗时。
- 当预计耗时数据不完整但存在安全的本地降级值时，系统应仍输出单值；数据置信等级只用于内部核验，不增加卡片文字负担。

### R2：计算定义

- 当用户浏览同方向目标站时，系统应按相邻站有向运行时分逐段求和，并加上目标线路站到具体卫生间的典型步行时间。
- 当用户已经到达所选起点站且路径需要乘车时，系统应计入起点实际乘坐线路、实际乘坐方向的首次期望候车时间。
- 当路径发生跨线换乘时，系统应增加具体换乘步行时间和换乘后线路的期望候车时间。
- 当路径需要在起点改乘反方向时，系统应使用目标方向的期望候车时间；只有存在经核实的额外站内换向步行数据时才增加该步行时间，V1 默认不额外叠加。
- 旧版 `reverseAtOrigin 4—6 分钟` 固定范围不得继承到 V2；普通线路锚点另一侧不能同时叠加固定掉头惩罚和目标方向首次候车。
- 当同一线路的支线路径不存在直达运行关系、必须换车时，系统应按一次同线换车处理；存在直达运行关系时不得重复增加换车惩罚。
- GPS 位置到所选起点站的地面步行、进站步行和安检不计入 ETA；计算起点表示用户已经到达该站，但尚未完成首次候车。

### R3：时间数据来源

- 当官方运营方公开相邻站时分或可推导时刻时，维护流程应优先使用官方公开信息。
- 当官方只提供到分钟的时刻时，系统应允许由相邻站时刻差推导典型运行秒数，并记录 `timetable_derived` 方法。
- 当官方数据缺失时，系统应按“同线公开资料 → 可核实公共资料 → 线路中位数 → 全局兼容值”的顺序降级，且每一条降级结果必须记录方法和来源状态。
- 正式使用的时刻、时分、换乘与步行数据必须固化为本地数据，不得在用户每次查询时请求第三方服务。

### R4：固定公式与舍入

- 当系统计算 ETA 时，应使用设计文档定义的统一秒级公式，最后只执行一次阶梯舍入；不得逐段先取整再相加。
- 当系统执行阶梯舍入时，应在小于 10 分钟使用 1 分钟刻度、10—30 分钟使用 2 分钟刻度、大于 30 分钟使用 5 分钟刻度；恰好处于半刻度时向上取整。
- 当候车间隔只有典型值时，期望候车时间应取该典型间隔的一半。
- V1 只使用线路／路径／方向的常态代表间隔，不随本地时间切换高峰、低峰或临时运行图；以后若引入分时段值，必须先补充独立需求和回归。

### R5：拓扑边界

- 当计算 4 号线环线路径时，系统应使用当前内圈或外圈的有向闭环边，不得把列表首尾误判为断开或掉头。
- 当计算支线路径时，系统应以明确的运行路径和服务模式为准，不得按 Excel 行相邻关系生成假边。
- 当目标卫生间与起点位于同一物理站时，系统应只计算站内换线／换向与前往具体卫生间所需的时间，不得增加列车运行区间。
- 当同一物理站的多条线路共享同一卫生间时，系统应复用同一设施实体，但允许为不同线路站配置不同步行时间。

### R6：本地完整基础数据

- 当小程序首次启动、断网或 CloudBase 不可用时，系统应使用随代码包发布的完整基础数据完成线路、站点、路径、卫生间和 ETA 查询。
- 当本地缓存存在已完整校验的新版本时，系统应优先使用该版本；不存在时回退到代码包基线。
- UI 结构、样式、交互和业务代码必须只随小程序代码包发布，CloudBase 数据不得改变页面结构或执行逻辑。

### R7：逻辑分层与发布单元

- 维护和运行数据应在逻辑上区分 `core`、`detail`、`eta`、`status`，但物理下载单元应依据实际体积决定。
- 当一个城市的待更新数据仍属于小数据时，发布流程应优先一次批量获取完整目标版本，而不是强制逐线路发起多个请求。
- 当未来体积实测达到拆分阈值时，manifest 可以声明多个不可变 part；客户端仍应整批校验并一次切换城市 `activeVersion`。
- 物理拆分采用项目工程阈值：`<= 256 KB raw` 使用单 part；`256—700 KB raw` 保持城市批量并把 part 控制在 `128—256 KB raw`；`> 700 KB raw` 才拆分；任一单模块 `> 512 KB raw` 时改用版本化文件或分页。上述数值不是平台官方硬限制。
- 发布流程应同时校验小程序端云函数响应 `1 MB`、单代码包 `2 MB`、全部分包 `30 MB`、本地缓存 `10 MB` 和网络接口并发 `10` 的平台边界，并预留 JSON 包装、版本缓存和后续城市增长空间。

### R8：版本与失败回退

- 当发布新数据版本时，发布端应先写入全部不可变数据内容，校验通过后最后更新版本清单。
- 当客户端取得新版本时，应先写入候选缓存并完成 schema、哈希、引用和完整性校验，全部成功后才切换 `activeVersion`。
- 当下载、校验或落盘任一步失败时，客户端不得部分覆盖当前有效版本，应继续使用旧缓存或代码包基线。

### R9：一城一工作簿

- 当新增城市时，维护流程应复制同一份空白 Excel 模板，每个城市使用一个独立工作簿，并保持工作表和字段完全一致。
- 工作簿应至少覆盖城市、线路、物理站、线路站、路径、路径站序、方向、换乘、卫生间、卫生间线路关联、相邻站时分、常规运营间隔、入口、来源和核实记录。
- 模板应明确区分“维护者必须确认”“可通过线上公开信息整理”“必须实地核实”“自动派生”四类责任。
- 记录 ID 必须稳定并持久化，不得根据 Excel 行号或显示顺序重新生成。

### R10：受控线上变更

- 当任务只实现本地数据模型、导入、计算和测试时，不得顺带创建集合、修改权限、上传正式数据或部署云函数。
- 当后续需要启用 CloudBase V2 发布时，执行方应先列出集合、索引、权限、兼容影响、回退方式和验证计划，并另行获得用户确认。

## 6. 核心验收指标

- 所有有卫生间卡片只出现一个整数分钟预计值。
- ETA 逐段使用秒级单值并包含首次期望候车，最终按 1／2／5 分钟阶梯舍入一次，重复运行结果稳定。
- 上海所有 active 运行边都有明确时间值或带来源等级的降级值。
- 环线闭环、支线共享区间、反方向、跨线换乘和同站卫生间均有回归用例。
- Excel 模板可以空白复制到任意城市，主键、外键、枚举和责任分级均可自动校验。
- 删除候选缓存或模拟云端失败后，完整上海查询仍由代码包基线正常工作。
- 体积测试记录上海现有运行 JSON `540,331 B raw / 59,549 B gzip`、ETA 预计 `66,610 B raw / 6,046 B gzip`；逐线路投影约 `711 KB raw / 91 KB gzip`，不得因强拆导致共享数据膨胀。
